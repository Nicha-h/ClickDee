# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

This backend has a layered structure (routes/services/schemas/middleware/db/config). `Campaign` is a full CRUD vertical slice (list/get/create/update/delete), `userId`-owned and behind `requireAuth` like every other resource — it used to be the unauthenticated reference slice before auth existed everywhere, that's no longer the case. It also has a `caption` field (nullable text) alongside name/status/budget/dates, plus the Meta Marketing API fields described in **Meta campaign hierarchy** below (`objective`, `specialAdCategories`, budget/bid fields, `meta*` id/status mirrors).

Auth: httpOnly session cookies protect every `User`-owned resource (`/api/auth/account/:id`, `/api/ai/*`, `/api/ai-memory/*`, `/api/campaigns/*`, `/api/notifications/*`). See **Auth** below before adding a new authenticated route. Domain models in Prisma: `User` with `Campaign` (now the root of the Meta object hierarchy — see **Meta campaign hierarchy** below for `AdSet`/`AdCreative`/`MediaAsset`/`Ad`/`AdInsight`), `Conversation`/`Message` (AI chat history), `AiMemory` (encrypted onboarding follow-up answers), `PendingAiAction` (staged AI-proposed campaign mutations awaiting human confirmation), and `Notification` all cascade-linked to it. See **AI campaign actions (human-in-the-loop)** under Product context for how the latter two fit together. Extend existing conventions rather than inventing new ones.

## Monorepo layout

`clickdee` (repo root) is a pnpm workspace (`pnpm-workspace.yaml`) with two packages: `frontend/` (a built-out Vite + React app — has its own `frontend/CLAUDE.md`) and `backend/` (this directory). Root `package.json` scripts (`dev`, `build`) delegate to both packages via `pnpm --filter`.

## Stack

- **Runtime/language:** TypeScript on Node.js
- **Web framework:** Hono (`hono` + `@hono/node-server`), with `@hono/zod-openapi` for route definitions validated by Zod and auto-generated OpenAPI docs, and `@hono/swagger-ui` serving interactive docs at `/docs`
- **ORM/DB:** Prisma (`prisma-client` generator, the no-Rust-engine TS client) targeting PostgreSQL through a driver adapter (`@prisma/adapter-pg` + `pg`). Prisma client generates into `src/generated/prisma` (gitignored)
- **Validation/tooling:** Zod, ESLint (flat config, mirrors `frontend/eslint.config.js` but with `globals.node`), Prettier (`semi: false`, `singleQuote: true`, same as frontend), Vitest
- **Auth:** `jose` (HS256 JWT sign/verify — see **Auth** below)
- **Package manager:** pnpm (workspace-level)
- **Dev runner:** `tsx` (loaded via `node --import tsx`), restarts on save via Node's native `--watch` (see note below on why `tsx watch` itself isn't used)

## Architecture

- `src/app.ts` builds and exports a side-effect-free `OpenAPIHono` app (routes mounted, `app.doc()`, Swagger UI, error handlers) — importable directly in tests via `app.request(...)` without binding a port.
- `src/server.ts` is the only place that calls `serve()`; it's the process entrypoint.
- No `controllers/` layer: `createRoute` + its handler stay colocated in `src/routes/<resource>.ts` (matching Hono's idiomatic style), but handlers delegate immediately to `src/services/<resource>.service.ts`, which owns all Prisma access. Routes never import `prisma` directly.
- `src/schemas/<resource>.schema.ts` holds the Zod shapes shared between the route's OpenAPI request/response schemas and the service's input types.
- `src/db/client.ts` exports a `globalThis`-cached `PrismaClient` singleton (avoids connection leaks across dev-mode restarts), constructed with a `PrismaPg` driver adapter (`@prisma/adapter-pg`) — **required** in Prisma 7's `prisma-client` generator; there is no Rust query engine binary anymore, so the client must be given either a driver `adapter` or an `accelerateUrl` at construction time, it can't read `DATABASE_URL` implicitly.
- `src/config/env.ts` parses `process.env` through Zod (`NODE_ENV`, `PORT`, `DATABASE_URL`, `AUTH_JWT_SECRET`, `AI_MEMORY_ENCRYPTION_KEY`, plus `GEMINI_API_KEY`/`GROQ_API_KEY` and their defaulted `*_BASE_URL` counterparts) and fails fast on misconfiguration. `AUTH_JWT_SECRET` (≥32 chars) and `AI_MEMORY_ENCRYPTION_KEY` (base64, decodes to exactly 32 bytes) are **required**, unlike the AI provider keys — generate each with `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` (secret) / `.toString('base64')` (key). See `.env.example`.
- `src/middleware/error-handler.ts` registers `app.notFound` and `app.onError` — call once from `app.ts` after routes are mounted.
- `src/middleware/auth.ts` exports `requireAuth` (a Hono middleware) and `AuthVariables` (the `{ userId: string }` context type). `src/lib/auth.ts` exports `signSessionToken`/`verifySessionToken` (JWT). See **Auth** below.
- `src/lib/encryption.ts` exports `encryptField`/`decryptField` (AES-256-GCM) for sensitive Prisma text columns. See **Sensitive data** below.
- `src/middleware/rate-limit.ts` exports a `rateLimit({ windowMs, max, key? })` factory — an in-memory, single-instance limiter keyed per client IP by default (`clientIp`), or by any `key` function (e.g. a constant for a global cap). See **Rate limiting** below.
- `src/app.ts` applies `hono/secure-headers` (strict `default-src 'none'` CSP on `/api/*`, `cross-origin` CORP on `/static/*` for the dev port split, defaults on `/docs`) and CORS from `env.CORS_ORIGINS`.
- `prisma/schema.prisma`: `generator client { provider = "prisma-client" }` (no Rust engine). The datasource block intentionally has **no `url`** — Prisma 7 forbids putting the connection string in the schema; `prisma.config.ts` supplies it to the CLI, and `src/db/client.ts` supplies it to the runtime adapter, both from `DATABASE_URL`.
- `tsconfig.json`: strict mode, ESNext/NodeNext modules, JSX configured for `hono/jsx`, output to `dist/`, excludes `**/*.test.ts` from the build (tests aren't shipped).

## Auth

httpOnly session cookies, not bearer tokens. `POST /api/auth/signup` and `POST /api/auth/login` sign a JWT (HS256, 24h expiry, `AUTH_JWT_SECRET`) and set it via `Set-Cookie: session=<token>; HttpOnly; SameSite=Lax` (see `lib/cookie.ts`'s `setSessionCookie`/`clearSessionCookie`) — the response body no longer includes the token. The browser attaches the cookie automatically on same-site requests; CORS is configured with `credentials: true` to allow this across the dev `localhost:5173` → `localhost:3000` port split. `POST /api/auth/logout` (`requireAuth`) clears the cookie server-side — there's no client-side token to simply drop anymore.

`requireAuth` (`middleware/auth.ts`) reads the `session` cookie via `hono/cookie`'s `getCookie`, not an `Authorization` header. It also enforces a lightweight CSRF check: any `POST`/`PUT`/`PATCH`/`DELETE` request through it must carry `X-Requested-With: XMLHttpRequest`, or it 403s — `SameSite=Lax` already blocks the cookie on most cross-site requests, this closes the remaining simple-cross-site-form gap without a double-submit token. `GET`/`HEAD` are exempt.

To protect a new route:

1. Type the app as `new OpenAPIHono<{ Variables: AuthVariables }>()` (see `routes/auth.ts` / `routes/ai.ts`).
2. Add `middleware: [requireAuth] as const` to the route's `createRoute({...})` config — `@hono/zod-openapi` infers the handler's context type from this, so `c.get('userId')` is typed without extra casts.
3. In the handler, read the caller's identity from `c.get('userId')` — **never** trust a client-supplied `userId` in the body/query/params for anything auth already tells you.
4. If the route also takes a resource id in the URL (e.g. `/account/:id`), `requireAuth` only proves _who_ the caller is — it does not check they own `:id`. Add an explicit `if (c.get('userId') !== id) return c.json({ message: 'Forbidden' }, 403)` (see `getAccountRoute`/`deleteAccountRoute`/`updateAccountRoute` in `routes/auth.ts`), or — the pattern used for `Campaign`/`AiMemory` — scope the resource query itself by `userId` so "not found" and "not yours" collapse into the same 404 without an extra existence-leaking check.

`PATCH /api/auth/account/:id` (`updateAccountRoute`) updates a caller-owned subset of `User` fields (`UpdateAccountSchema` in `auth.schema.ts`: `name`, `email`, `businessName`, `location`, `category`, `budget`, `signatureProduct`, `customerPersona` — a deliberately narrower set than every column on `User`, scoped to exactly what the frontend's account page edits) via `user.service.ts`'s `updateUser`. Same ownership check as `GET`/`DELETE /account/:id`. A Prisma `P2002` (unique constraint, i.e. the new `email` is already taken) maps to 409; `P2025` (record not found) maps to 404. `User.name` (nullable, no signup-time source — starts empty) and `User.customerPersona` (nullable `@db.Text`, free-text "AI insight" the user edits directly, not actually AI-generated) were added to the schema specifically to back this route and the account page's "ชื่อ-นามสกุล"/"AI Insight" fields, which had no backing column before.

`Campaign` is behind `requireAuth` and scoped per-owner (`Campaign.userId`), same as `AiMemory`/`Conversation`. It was the plain-CRUD reference slice before auth existed; that's no longer the case, so don't treat it as the unauthenticated example anymore.

## Sensitive data

`AiMemory.question` and `AiMemory.answer` are both encrypted at rest with AES-256-GCM (`lib/encryption.ts`, key from `AI_MEMORY_ENCRYPTION_KEY`) — encrypt immediately before the Prisma write, decrypt only where actually needed (`getAiMemoryQas`/`getAiMemoryItems` in `services/onboarding.service.ts`, used by the AI chat context and the account-page AI Memory viewer respectively). `question` used to be left in plaintext (it's the AI's own generated prompt text, not user-typed input) but is now encrypted too for defense-in-depth, since it's dynamically generated per business context and could hint at business specifics in aggregate. Follow this same pattern (encrypt at the service layer, right before the write) for any new column holding user-authored business/PII content.

Full Postgres row-level security (RLS) and transparent data encryption (TDE) at the database layer are a deliberately separate, larger future initiative — not part of this field-level encryption. TDE is a setting on the Postgres hosting provider, not application code. RLS would need a non-superuser app DB role, policy migrations, and per-request session-variable middleware; don't attempt it as a side effect of a "should this field be encrypted" change.

**PII redaction of AI chat input** (`lib/pii-filter.ts`'s `redactPii`) is a separate, complementary mechanism to the encryption above — it doesn't encrypt-then-decrypt, it strips sensitive spans out of the text entirely before the text exists anywhere else. `ai.service.ts`'s `sendMessage` calls it as the very first line, before the user's message is written to `Message.content` or included in the history sent upstream, so redacted content never reaches either the DB or whichever third-party model actually serves the request (see **AI provider cascade** below). It's a best-effort regex pipeline (email, phone, IPv4/IPv6, Luhn-checked card numbers, long bank-account-like digit runs, Thai/English address keywords, "my name is"/"ชื่อ...คือ" name patterns) — not NER-grade, and known to miss bare real names outside those trigger phrases. This is a deliberate, documented v1 scope decision (see PDPA notes below), not an oversight to silently "improve" with a model-based second pass without discussing the added latency/cost/third-party-dependency tradeoff first. Scope is strictly the user's free-text chat prompt — never applied to an AI-proposed campaign `caption`, which may legitimately contain a real business phone number. `Message.redacted` (boolean) records whether a given message was altered, surfaced to the frontend so the user sees a visible notice rather than silently having their input rewritten (PDPA Sec 23 transparency).

## AI provider cascade

`src/lib/openai.ts`'s `createChatCompletion` is the only place any service talks to an AI provider — services never construct an SDK client or pick a model themselves. It walks a hardcoded, pinned six-tier `CHAIN` (3x Gemini, then 3x Groq, both OpenAI-compatible endpoints reached via the plain `openai` SDK with a different `baseURL`) on every call: on a 429 (`RateLimitError`), a connection error/timeout (`APIConnectionError`, which `APIConnectionTimeoutError` extends), or a provider-side 5xx (`InternalServerError`) it puts that exact model id on cooldown (`Retry-After` header if present for a `RateLimitError`, else a 60s default — a connection/5xx error has no such header, so it always gets the 60s default) and tries the next tier for that same request; a fully successful call updates a module-level `currentIndex` so the _next_ request starts from the tier that actually worked, not back at the top — this is deliberate, not a bug, since immediately retrying the top tier would just re-trigger the same failure. `currentIndex` is only promoted back to 0 once the top tier's own cooldown has passed (checked lazily at the start of each call). Model ids are intentionally hardcoded, not env-configurable — cooldowns are tracked per exact model id, and a `-latest`-style alias would silently break that tracking. A content-filtered response is a normal 200 with `finish_reason: 'content_filter'`, not an exception, so it never triggers cascade or retry — only the three availability-error types above do; everything else (bad requests, auth errors, unexpected exceptions) rethrows immediately. If neither `GEMINI_API_KEY` nor `GROQ_API_KEY` is set, `createChatCompletion` throws `AiNotConfiguredError`; if only one is set, the other provider's tiers are silently skipped rather than erroring. `AllTiersExhaustedError extends AiRateLimitError`, so the existing `err instanceof AiRateLimitError` → 429 mapping in `routes/ai.ts`/`routes/onboarding.ts` catches it without any route changes. `ai.service.ts`'s `sendMessage` additionally wraps its call to `generateAssistantReply` and, for any error other than `AiContentFilterError`/`AiNotConfiguredError` (i.e. `AllTiersExhaustedError` or anything else the cascade couldn't route around), persists a friendly Thai apology as the assistant's reply instead of throwing — the user's own `Message` row is already committed by that point in `sendMessage`, so propagating the error would otherwise leave it stranded with no reply in the thread.

## Caption research pipeline (Distiller → cache → Compound → Formatter)

`src/lib/compound.ts`'s `researchForCaption` sits in front of AI-proposed campaign captions in `ai.service.ts`'s `generateAssistantReply`, to ground captions in real-time context (trends, weather, seasonal angles) without burning Groq's `groq/compound` model's tight free-tier quota (30 RPM / 250 RPD / 70K TPM). It runs only when the first chat completion's tool call is `stage_create_campaign`, or `stage_update_campaign` with a non-empty `caption` — never on plain conversation turns, and never for `stage_delete_campaign`. `src/lib/distiller.ts`'s `distillCaptionRequest` (Stage 0) is a small structured-extraction call through the normal cascade (never Compound) that normalizes the request into `{researchQuery, tags}`, which is hashed into a deterministic `cacheKey` in code (not by the model) — this is what lets two differently-worded requests about the same underlying topic hit the same cache entry. `src/lib/compound-cache.ts` is an in-memory `Map<cacheKey, {value, expiresAt}>`, same single-instance convention as the rate limiter above; a cache hit skips calling Compound entirely. On a miss, `compound.ts` calls Compound directly via `getGroqClient()` (an additive export from `lib/openai.ts` that reuses the cascade's client-construction options) — deliberately outside the six-tier `CHAIN`, since Compound must never occupy a cascade slot or share cooldown state with the chat tiers. TTL is picked by tag (`COMPOUND_CACHE_WEATHER_TTL_SECONDS` if the Distiller tagged the request `weather`, else `COMPOUND_CACHE_DEFAULT_TTL_SECONDS`). The whole pipeline fails soft at every stage (`console.error` + `null`) — a broken distillation or a Compound error never blocks staging, the caption just stays as the model's original draft.

Because `stagePendingAction` already writes the model's draft caption immediately (see **AI campaign actions** below), findings can't just be folded into the existing second completion call's prompt without a mismatch: the model could _say_ an improved caption while the actually-staged `PendingAiAction.payload.caption` stays stale. Instead, the tool result fed into that second call carries a `research` field plus an instruction to wrap any revised caption in `[[CAPTION]]...[[/CAPTION]]` (same convention as the existing `[[NEXT]]` bubble separator). `generateAssistantReply` regex-extracts that marker from the second call's reply, calls `pendingActionService.updatePendingActionCaption` (same atomic `status: 'PENDING'` guard as `confirmPendingAction`/`cancelPendingAction`) to revise the staged payload, and strips the marker before the text reaches the user. If the model omits the marker, the caption safely stays as the pre-research draft — this is a soft edge case, not a crash.

`src/lib/ai-live-test-guard.ts` is scaffolding for future opt-in live (non-mocked) AI tests — `recordLiveCall` caps real provider calls per test run (`MAX_LIVE_CALLS_PER_RUN`, with a lower `MAX_LIVE_COMPOUND_CALLS_PER_RUN`) and logs every one, so a bug that turns one intended live call into a retry storm can't silently exhaust a day's Compound quota. No live test file exists yet — `vitest.live.config.ts` / `pnpm test:live` only matches `*.live.test.ts`, which the default `vitest.config.ts` explicitly excludes, so `pnpm test`/`test:watch` never make real API calls.

## Rate limiting

`middleware/rate-limit.ts`'s limiter keeps its counters in an in-memory `Map` (stale keys are swept periodically) — it works correctly for a single process but does **not** coordinate across multiple instances. Client identity never comes from `X-Forwarded-For` (client-controlled, so trusting it let anyone reset their limit per request); `X-Real-IP` is used only when `TRUST_PROXY=true` (set in the `Dockerfile`, where nginx overwrites it), otherwise the socket address. It's applied to `POST /api/onboarding/followup-question` because that route is unauthenticated (see below) and spends real AI provider budget per call (Gemini or Groq — see **AI provider cascade** above). This is intentional tech debt, deliberately left as-is while the app runs as a single backend process — the trigger condition to revisit it is any horizontal scale-out (multiple instances behind a load balancer, serverless scale-to-many, etc.), at which point it must move to a shared store (Redis or similar) or per-instance limits become trivially bypassable by spreading requests across instances. Don't treat the in-memory implementation as an oversight to "fix" before that trigger condition is actually met.

`POST /api/onboarding/followup-question` is the one intentionally public, unauthenticated endpoint in the API: it runs during onboarding, before an account/token exists, and only proxies to the AI (no DB write), so it carries no PII-at-rest risk. It's guarded by a per-IP limiter, a global daily cap (`FOLLOWUP_DAILY_CAP`, bounds total AI spend even across rotating IPs), and request size caps instead of `requireAuth`.

### DATABASE_URL: use a plain `postgres://` connection string, not `prisma+postgres://`

`@prisma/adapter-pg` connects over the raw Postgres wire protocol via `pg` — it **cannot** talk to Prisma's own `prisma+postgres://` proxy scheme (that's a different, HTTP-based protocol meant for Prisma Accelerate/managed Prisma Postgres, and the connection just hangs/terminates if you hand it here). If using the local Prisma Postgres dev server (`npx prisma dev --detach`), use the **direct** connection string it prints (`postgres://postgres:postgres@localhost:<port>/template1?sslmode=disable`, one port above the main port it's listening on) as `DATABASE_URL`, not the `prisma+postgres://...` one. Both the CLI (via `prisma.config.ts`) and the app (via `src/db/client.ts`'s adapter) read the same `DATABASE_URL`. In a real deployment, `DATABASE_URL` is just whatever standard Postgres connection string the provider gives you — this local-dev two-protocol quirk goes away entirely.

### Why `dev` uses `node --watch --import tsx` instead of `tsx watch`

`tsx watch` is the more common choice and works fine when you run `pnpm --filter backend dev` directly. But on this project's Windows dev environment, `tsx watch`'s own child-process-based restart mechanism never completes when it's invoked through an extra layer of process wrapping — specifically when run via the root `pnpm dev` (which uses `concurrently` to run frontend and backend together): the process starts but silently never binds the port. `node --watch --import tsx` doesn't have this problem (Node's built-in watch restarts the process natively rather than spawning a child over IPC) and works reliably both standalone and under `concurrently`. `src/server.ts` registers `SIGINT`/`SIGTERM` handlers that call `server.close()` before exiting, so the port is released cleanly on restart. If this turns out to be specific to one machine/Node version rather than a general Windows issue, `tsx watch` is a reasonable thing to revisit.

## Meta campaign hierarchy (Campaign → Ad Set → Ad Creative → Ad) + Insights

Real Meta Marketing API object creation, on top of the `Campaign` model — previously this was research-only (`docs/meta-marketing-api-findings.md`); the Prisma models, HTTP client, services, routes, and AI-staging integration now actually exist. Object hierarchy and Prisma models: `Campaign` (extended with `objective`, `specialAdCategories`, `bidStrategy`/`bidAmount`, `buyingType`, `campaignBudgetOptimization`, `dailyBudget`/`lifetimeBudget`, and `meta*` mirror fields) → `AdSet` → `AdCreative` (+ `MediaAsset` for uploaded images/video) → `Ad`, plus `AdInsight` for stored performance metrics. `optimizationGoal`/`billingEvent`/`destinationType`/`dsaBeneficiary` and all `meta*` status/id fields are plain `String` columns, not Prisma enums — Meta's own vocabularies there are large and evolve independently of our releases; validate the ones that matter at the Zod layer (`schemas/ad-set.schema.ts`) instead.

**Safety-critical: PAUSED-by-default, two explicit Meta-facing actions only.** Every object this app creates locally (`Campaign`, `AdSet`, `AdCreative`, `Ad`) is a plain DB row — no HTTP call to Meta happens as a side effect of any create/update route. Exactly two service functions in `services/meta-publish.service.ts` ever call the Meta API to create or activate something, and nothing else does:
- `publishCampaignToMeta` (`POST /api/campaigns/:id/publish-to-meta`) pushes the whole local hierarchy to Meta in order (campaign → ad sets → creatives → ads), **forcing `status: 'PAUSED'` on every object regardless of what's stored locally**. It's idempotent per level — an object that already has a `meta*Id` is skipped, so re-running after a partial failure only pushes what's still missing.
- `setMetaStatus` (`POST /api/campaigns/:id/meta-status`) is the **only** path that can push `ACTIVE` to Meta — and it cascades to child ad sets and ads, since Meta requires all three enabled to actually deliver, not just the campaign.

Never add a code path that sends `status: 'ACTIVE'` to Meta outside `setMetaStatus`, and never let campaign/ad-set/ad creation default to anything but `PAUSED` — this is the mechanism that prevents an SME from accidentally spending money.

**No real per-user Meta connection exists yet.** `config/meta.ts`'s `getDevMetaCredentials()` reads a single dev/test Business Manager's credentials from optional env vars (`META_DEV_ACCESS_TOKEN`/`META_DEV_AD_ACCOUNT_ID`/`META_DEV_PAGE_ID`/`META_DEV_INSTAGRAM_USER_ID`, see `.env.example`) — a stand-in for the not-yet-built Facebook Login for Business OAuth connect flow (`docs/meta-marketing-api-findings.md` section 4). Every service that needs to call Meta reads credentials through this one function, so swapping in real per-user token storage later is a one-function change, not a repo-wide search. When unset, `publishCampaignToMeta`/`setMetaStatus`/the media upload routes throw `MetaNotConfiguredError`, mapped to a 400 by the global error handler rather than crashing.

**`env.META_SIMULATE_PUBLISH` — demo/offline escape hatch, off by default.** Real sandbox credentials work end-to-end for `Campaign`/`AdSet`/media upload, but Meta rejects Ad Creative/Ad creation ("post was created by an app that is in development mode") until the Meta App Dashboard app is switched Development → Live — a change deliberately avoided right before a live product demo. When this flag is `true`, every function in `meta-publish.service.ts` and `media.service.ts` that would call `metaRequest`/`metaUploadFile` instead skips the network call and writes a `simulatedMetaId(...)`-generated fake id (`sim_<kind>_<uuid>`, never mistakable for a real Meta id) plus the same `PAUSED`/`ACTIVE` status a real call would have produced. All local validation (`assertCampaignReadyForMeta`/`assertAdSetReadyForMeta`, Zod schemas) still runs unchanged — only the actual Meta HTTP call is skipped. This is temporary/demo-scoped, not the intended normal dev path; flip it back to `false` (or unset) once real Meta calls are viable again (e.g. after switching the app to Live mode).

**Local-draft-first validation.** Task-1-style "required by Meta" rules (objective must be ODAX, a budget is required when `campaignBudgetOptimization` is on, etc.) are deliberately **not** all enforced at local `Campaign`/`AdSet` creation time — `campaignBudgetOptimization` defaults to `true`, so enforcing "budget required when CBO is on" in the Zod schema would reject every in-progress draft that hasn't set a budget yet (this was a real regression caught during implementation; see the regression-guard test in `schemas/campaign.schema.test.ts`). Structural rules that don't depend on a defaulted field (bid strategy ↔ bid amount, daily vs. lifetime budget mutual exclusivity) are still enforced in `schemas/campaign.schema.ts`'s `superRefine`. The "fully ready for Meta" check lives in `meta-publish.service.ts`'s `assertCampaignReadyForMeta`/`assertAdSetReadyForMeta`, which read the actual stored row — this is what lets a campaign be built up incrementally (e.g. via the AI staging flow below) before it's ready to publish.

**Meta HTTP client & error mapping.** `lib/meta-client.ts`'s `metaRequest`/`metaUploadFile` wrap the Graph API (base URL/version centralized in `config/meta.ts`'s `META_API_VERSION` — bump in one place when Meta deprecates a version). `metaRequestWithRetry` adds exponential backoff + jitter specifically for `MetaRateLimitError`. Four typed error subclasses map to HTTP codes in `middleware/error-handler.ts`'s global `onError` (not per-route try/catch): `MetaTokenExpiredError` (code 190) → 401 + `reauth: true`, `MetaRateLimitError` (17/32/613) → 429, `MetaInvalidParameterError` (100) → 400 with Meta's own `error_user_msg` surfaced when available, `MetaPolicyViolationError` (2635) → 422 "needs revision". `AdSetValidationError`/`AdCreativeValidationError`/`MetaPublishValidationError` (this app's own validation, e.g. a Lead-gen ad set missing `promoted_object`) map to 400 the same way.

**Ad Creative "thin abstraction".** `services/ad-creative.service.ts`'s `buildObjectStorySpec(format, ...)` is the one function that turns our own `format` (`IMAGE_POST`/`VIDEO_POST`/`REELS`/`CAROUSEL`/`STORY`) + copy fields into Meta's `object_story_spec` shape — callers (routes, and eventually the AI layer) never need to know Meta's shapes directly. Media (`schemas/ad-creative.schema.ts` inputs reference our own `mediaAssetId`, not a raw Meta `image_hash`/`video_id`) must already be uploaded and `READY` (`services/media.service.ts`'s `uploadImage`/`uploadVideo` + `pollVideoStatus` for async video processing) before a creative can reference it.

**Zod + `@hono/zod-openapi` gotcha:** `schemas/ad-creative.schema.ts` deliberately imports `z` from plain `zod` (with a side-effect `import '@hono/zod-openapi'` to keep `.openapi()` available) instead of `@hono/zod-openapi`'s own re-exported `z`. Going through the re-exported `z` for a `z.discriminatedUnion` with a nested array-of-objects field (`childAttachments`) silently collapsed that field's inferred type to `any` with this zod/`@hono/zod-openapi` version pair, breaking discriminated-union narrowing in `ad-creative.service.ts`'s `switch (input.format)`. Confirmed via isolated repro before working around it — if a similar "implicitly `any`" narrowing failure shows up in a new schema with nested array-of-object fields, try the same plain-`zod`-import fix before assuming the surrounding code is wrong.

**AI staging flow.** `stage_create_campaign` (see **AI campaign actions** above) now also accepts optional `objective`/`specialAdCategories`/`campaignBudgetOptimization`/`creativeFormat`/`ctaType` — included only when the conversation makes them clear, per the updated system prompt. `confirmPendingAction`'s `CREATE` branch converts the staged THB `budget` to Meta's minor-unit (satang) `dailyBudget` (open-ended schedule) or `lifetimeBudget` (fixed end date), and cascades creating one default local `AdSet` (Advantage+ audience + placements, `optimizationGoal` mapped from the staged objective) via `createDefaultAdSet`. It deliberately does **not** cascade-create an `AdCreative`/`Ad` even when `creativeFormat` was staged — every supported format needs an uploaded image/video first, and media can't be attached through a chat tool call; that stays a manual follow-up step through `routes/media.ts` + `routes/ad-creatives.ts`.

**Insights.** `services/ad-insight.service.ts`'s `fetchInsights` pulls the Task-6 field set from `GET /{node}/insights`; `storeInsights` upserts into `AdInsight`. The upsert key (`level, campaignId, adSetDedupKey, adDedupKey, dateStart, dateStop, publisherPlatform, placement`) uses `''` **sentinel strings**, not `null`, for the dimensions that don't apply at a given level/breakdown — Postgres treats `NULL` as distinct from `NULL` in a unique index by default, so nullable columns there would let duplicate campaign-level rows slip past the upsert silently. These dedup-key columns are kept separate from the real nullable `adSetId`/`adId` foreign keys (used only for cascade-delete integrity) specifically so a `''` sentinel never has to satisfy a foreign-key constraint. `routes/insights.ts` reads stored rows by default and only calls Meta live when `?refresh=true` is passed, per Task 6's guidance to cache/schedule pulls rather than hit Meta on every dashboard view — there's no job scheduler in this codebase to run that on a cadence yet (same deliberate-tech-debt category as the in-memory rate limiter above); `syncInsightsForCampaign` is the entrypoint a future one would call.

## Cloudinary media hosting (preview URLs, not required for Meta)

`MediaAsset` uploads (`services/media.service.ts`'s `uploadImage`/`uploadVideo`) also push the same bytes to Cloudinary via `lib/cloudinary-client.ts`'s `uploadBufferToCloudinary` (a `Buffer` piped into the SDK's `upload_stream`, wrapped in a Promise since that API is callback-only), independent of and in addition to the Meta `adimages`/`advideos` upload described above. This exists purely to give the frontend an immediate, reliable preview — Meta's own upload response only ever returns a URL for real (non-simulated) *image* uploads, never video, never simulated-mode, so there was previously no way to preview a freshly-uploaded asset before the underlying ad was actually published.

Cloudinary's result is written into new `MediaAsset.cloudinaryUrl`/`cloudinaryPublicId` columns — deliberately **separate** from the pre-existing `sourceUrl` column, which stays exactly as Meta populates it (real image uploads only). `resolveMediaAssetPreviewUrl(asset)` (exported from `media.service.ts`) is the one place "which URL do we show" is decided (`cloudinaryUrl ?? sourceUrl`) — both `routes/media.ts`'s `serializeMediaAsset` (as `previewUrl`) and `ad-creative.service.ts`'s `mediaRefFromImageHash`/`mediaRefFromVideoId` (as `mediaAssetUrl`) go through this helper rather than reading either column directly, so a future third URL source is a one-function change.

`config/cloudinary.ts`'s `getCloudinaryCredentials()` follows the exact same "optional, three vars, `null` if any unset" shape as `getDevMetaCredentials()`. Unlike Meta, a missing/failed Cloudinary call in the live upload path is **non-fatal** — `media.service.ts`'s `tryUploadToCloudinary` wraps it in try/catch and only `console.error`-logs, because Meta's `metaImageHash`/`metaVideoId` (not Cloudinary) are the actual hard requirement for publishing a creative, and Cloudinary being briefly down shouldn't block that. Cloudinary uploads run even when `env.META_SIMULATE_PUBLISH` is true — that flag exists solely to work around Meta's Development-mode app restriction (see above) and has no bearing on whether Cloudinary hosting should also happen. `MediaAsset.cloudinaryPublicId` is set to the same value as our own `MediaAsset.id` (used as Cloudinary's `public_id`) so a human can correlate a row to its Cloudinary asset without the DB, and so a future delete/re-upload path has what it needs — no delete path exists yet, since nothing in this codebase currently deletes a `MediaAsset` row outside of cascade deletes.

`scripts/seed-admin810.ts`'s placeholder images are uploaded to Cloudinary too (reusing the same `uploadBufferToCloudinary` helper, into `cloudinaryUrl` — `sourceUrl` stays `null` for seed rows since there's no Meta upload at all), replacing their old `/static/placeholders/...` relative-path URL. Unlike the live upload path, a missing/failed Cloudinary call in the seed script is **fatal** (throws) — there's no independent fallback the way Meta's hash provides one for a real upload, so a seed run that would silently produce broken image URLs fails loudly instead. This incidentally sidesteps (without fixing) a real gap where those placeholders 404 in production, since the `Dockerfile` never copies `backend/static/` into the runtime image — the `/static/*` route itself (`app.ts`) is left in place regardless, since it's generic infra, not specific to this one use case.

## Deployment

`Dockerfile` builds both packages into a single image; `docker/entrypoint.sh` starts the backend (`node .../server.js`) and nginx as sibling background processes, then `wait`s on the backend specifically. If the backend exits (e.g. crashes at boot on a missing env var), the entrypoint kills nginx and exits with the backend's code, so the container as a whole is reported unhealthy/failed instead of nginx staying up and silently 502-ing every `/api/*` request forever.

## Product context

Based on the sibling `frontend/` app's pages, ClickDee is an ad-campaign management/analytics platform: users connect ad accounts (e.g. Facebook), create and manage campaigns, and view AI-assisted performance reports. The `Campaign` model/routes were the first real slice of that; the full Meta object hierarchy (ad sets/creatives/ads) and stored Insights now exist too (see **Meta campaign hierarchy** below) — what's still unbuilt is the per-user OAuth connection flow that would let a real SME's own ad account authenticate (current Meta calls use a single dev/test credential set). Onboarding now has a real AI-driven follow-up loop (`routes/onboarding.ts` + `services/onboarding-ai.service.ts`): after the user fills in base business info, the AI asks up to `MAX_FOLLOWUP_QUESTIONS` (5) clarifying questions one at a time — capped server-side and fail-safe on any AI/parse error — and the answers are persisted as `AiMemory` at signup, only if the user explicitly consented. The system prompt also treats a vague/non-answer (e.g. "ไม่ทราบ", "ไม่แน่ใจ", "idk") as insufficient to finish the flow — the model is instructed to ask a different, more concrete question (narrower scope, concrete example) instead of repeating the same abstract one or ending early. Beyond the prompt instruction, `generateFollowupQuestion` now backs that up with a programmatic character-bigram similarity check against previously-asked questions (Thai text doesn't reliably space-delimit words, so this is bigram-based rather than word-overlap) — a likely-repeat or a parse/schema-validation failure triggers exactly one retry (with an extra corrective note appended to the prompt) before falling back to `done:true`, and every fail-safe path now logs via `console.error` so premature endings are debuggable. Follow-up questions can also be multiple-choice now (`FollowupResult`/`FollowupQuestionResponseSchema`'s `type: 'text' | 'choice'` + `choices: string[] | null`), when the model judges the answer space is a small fixed set.

AI chat (`routes/ai.ts` + `services/ai.service.ts`) replies may now span multiple chat bubbles: the model is instructed to separate distinct points with a line containing exactly `[[NEXT]]`, which `sendMessage` splits and persists as one `Message` row per bubble (sequential, not `Promise.all`, so `createdAt` ordering stays deterministic) — `POST /api/ai/messages` returns `assistantMessages: AiMessage[]` (plural) instead of a single message. Markdown tables are now allowed in replies (previously forbidden in the prompt). The assistant uses OpenAI SDK native function-calling (`onboarding-ai.service.ts` instead uses `response_format: json_object` for its own JSON output — that distinction still holds).

### AI campaign actions (human-in-the-loop)

The assistant has three tools — `stage_create_campaign`, `stage_update_campaign`, `stage_delete_campaign` — and **none of them mutate `Campaign` directly**. `ai.service.ts`'s `executeToolCall` only calls `pending-ai-action.service.ts`'s `stagePendingAction`, which writes a `PendingAiAction` row (`type`, `targetCampaignId`, a Zod-validated `payload` JSON blob, `status: PENDING`) and returns a tool result telling the model the action is staged-only. The model's follow-up reply is instructed to state the proposal in plain language (name/budget/schedule/caption for create/update) and ask the user to confirm — it must never claim the action already happened. This is the actual security boundary for "AI can't act on its own": there is no code path from a tool call to a Prisma `campaign.create/update/delete` call, only through the confirm endpoint below, which requires the authenticated session user to explicitly invoke it. None of the three tool JSON schemas expose a `status`/`publish` field either, so the model can never request `ACTIVE` even under prompt injection — `payload.proposedStatus` is always hardcoded to `'DRAFT'` server-side when staging.

`POST /api/ai/actions/:id/confirm` (body `{publish: boolean}`, default `false`) is the only code path that executes the staged action — `pending-ai-action.service.ts`'s `confirmPendingAction` atomically claims the row first (`updateMany({where: {..., status: 'PENDING'}})`, checking `count`) before touching `Campaign`, closing a confirm/cancel race window. `publish: true` is the only way a `CREATE` action's campaign ends up `ACTIVE` instead of `DRAFT`, or an `UPDATE` action's target gets `status: 'ACTIVE'` — that decision belongs solely to the human clicking confirm, never the model. `POST /api/ai/actions/:id/cancel` (`cancelPendingAction`) uses the same atomic-claim pattern to move `PENDING → CANCELED`. A `PendingAiAction` past a 24h TTL is opportunistically flipped to `EXPIRED` inside `stagePendingAction`'s own cap check (max 5 concurrent `PENDING` per user) rather than via a cron job — there's no job scheduler in this codebase, same category of deliberate tech debt as the in-memory rate limiter above.

`Notification` (`routes/notifications.ts` + `services/notification.service.ts`) is a real backend model now, not frontend-only mock data. `sendMessage` creates one (`type: 'AI_TASK'`) whenever a tool call stages an action; its `link` is `null` for a `CREATE` (no campaign exists yet) until `confirmPendingAction` fills it in as `/campaign/:id` once the campaign is actually created — the frontend's notification bell polls `GET /api/notifications` (no websocket/SSE in this codebase) and uses that `link` for click-to-navigate. A `Message` can carry a `pendingActionId` (the **last** bubble of a staging turn) so `GET /api/ai/messages` returns the confirm-card data inline with the chat history, no second round-trip needed.
